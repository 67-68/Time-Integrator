# 补充说明

## 功能

#### **宪法第一条：关于“耦合性”——神圣的“职责分离”**

*   **你的问题：** 卡片和干涉，是强绑定还是弱耦合？
*   **最终裁决：** **绝对的、彻底的、永恒的弱耦合。**
*   **第一性原理：**
    1.  **“物种”不同：** 一个`InsightCard`（洞察卡片），是一个**对“过去”的、不可变的“事实陈述”**。它是一位“**历史学家**”。而一个`Intervention`（干预），是一个**对“未来”的、有状态的“行为契约”**。它是一位“**行动规划师**”。
    2.  **“职责”不同：** `InsightManager`的职责，是生成和管理“历史事实”。我们**绝对不能**污染它的数据模型。我们必须创建一个**全新的、独立的“物种”和“管理者”**。
*   **行动指令：**
    *   我们将创建一个全新的数据类，名为 `InterventionContract`（干预契约）。
    *   这个`InterventionContract`将通过`insight_card_uuid`，**单向地、弱耦合地**，引用它所源于的那张卡片。

#### **宪法第二条：关于“状态管理”——“契约”必须被“存档”**

*   **你的问题：** 内存，还是持久化？
*   **最终裁决：** **必须持久化。**
*   **第一性原理：** 用户的“承诺”，是系统中最宝贵的数据资产之一。它是一个**有生命周期的实体**（待激活 -> 已触发 -> 已完成/已忽略）。一个会在程序关闭后就“失忆”的系统，是一个**不值得信任**的系统。
*   **行动指令：**
    *   我们将创建一个全新的服务，名为`InterventionService`（或`CommitmentService`）。
    *   它的核心职责，就是**管理所有`InterventionContract`的生命周期**，包括将它们**创建、读取、更新、并持久化**到一个专门的存储文件（如`commitments.json`）中。

#### **宪法第三条：关于“数据流”——严禁“双向同步”，拥抱“单一信源”**

*   **你的问题：** 提醒时，是复制卡片，还是直接使用原界面？
*   **最终裁决：** **永远、永远、永远不要复制状态。永远直接使用（或导航至）那个“单一真理之源”。**
*   **第一性原理：** 你的直觉是完美的。复制数据，就是**在你的“共和国”里，创造了两个政府**。它们之间的数据同步，将成为你未来所有bug和混乱的根源。
*   **行动指令：**
    *   那个“行动提醒”的模态窗口，**不应该**包含任何复杂的“卡片渲染”逻辑。
    *   它的核心交互应该是：
        1.  **展示一个极其简洁的提醒文本**（由`InterventionService`提供）。
        2.  提供两个核心按钮：**[ 查看详情 ]** 和 **[ 忽略 ]**。
        3.  当用户点击 **[ 查看详情 ]** 时，这个窗口的**唯一职责**，就是向`MainWindow`（我们的“中央政府”）发出一个**导航请求**，请求`MainWindow`将视图切换到`AnalysisPage`，并**命令**`AnalysisPage`的`Presenter`，滚动并高亮到那个与“契约”相关联的`insight_card_uuid`所对应的卡片上。

#### **宪法第四条：关于“物种分类”——为“卡片”进行“灵魂移植”**

*   **你的问题：** 需要一个逻辑卡片类，作为GUI卡片的Controller吗？
*   **最终裁决：** **是的。这不仅是“需要”，这是我们通往一个可测试、可维护、可扩展架构的唯一道路。**
*   **第一性原理：** 我们必须严格遵守我们在之前讨论中，已经确立的**MVP（Model-View-Presenter）架构模式**。
*   **行动指令：**
    *   **Model（灵魂）：** 我们将创建一个纯粹的、与UI无关的`LogicalInsightCard`数据类。它包含了这张卡片所有的数据和状态。`InsightManager`只生产和管理这种“灵魂”。
    *   **View（肉体）：** 我们的`InsightCardWidget`（继承自`QWidget`），将成为一个“**愚蠢的**”、只负责“**展示**”的“肉体”。它不包含任何业务逻辑。
    *   **Presenter（大脑）：** 每一个`InsightCardWidget`，都将拥有一个与之对应的`InsightCardPresenter`实例。这个`Presenter`负责：
        1.  从`Manager`获取一个`LogicalInsightCard`（灵魂）。
        2.  将“灵魂”中的数据，填充到它所控制的“肉体”(`Widget`)中。
        3.  处理“肉体”上发生的所有用户交互（如按钮点击），并决定如何更新“灵魂”（通过调用`Manager`或`InterventionService`）。

# 搁置的灵感

## Archive 界面设计灵感

### 界面展示方案
- 时间轴 + 详情面板：状态转换可视化展示
- 仪表盘 + 列表：统计概览 + 详细记录组合
- 聊天记录风格：模拟对话流的时间线
- 三层架构：筛选层 + 列表层 + 详情层
- 卡片网格 vs 表格列表的权衡

### 功能模块构想
- 多维度筛选：按类别/日期/状态组合过滤
- 成功率统计和趋势分析
- 失败原因分类和模式识别
- 最佳干涉时机数据挖掘
- 导出行为改变效果报告
- 跨时间的模式演化追踪

### 架构设计思路
- Evidence Repository：统一历史证据存储
- Archive Entry 数据模型：contract + feedback + tags
- 分离展示与输入：只读查看 + 独立输入对话框
- 二次干涉理念：成功/失败记录作为新的数据收集
- 洞察-干涉-验证的完整学习循环
- JsonRepositoryInterface 接口扩展需求

### 哲学思考
- 行为科学实验室概念：观测→假设→实验→验证
- 时间性质区分：当下洞察 vs 历史档案
- 认知负荷考量：避免分析界面信息过载
- 反思空间设计：专门的历史回顾环境

### 交互设计灵感
- 渐进式信息展开：简洁默认视图 + 按需详情
- 上下文跳转：从 archive 链接到相关洞察
- 实时反馈：输入时即时显示统计更新
- 批量操作：支持批量标记和分析
